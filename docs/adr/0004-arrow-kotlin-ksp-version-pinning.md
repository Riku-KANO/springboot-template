# ADR 0004: Arrow を 2.2.2 に固定し、Kotlin/KSP のバージョンと連動させる

## ステータス

Accepted

## コンテキスト

`gradle/libs.versions.toml` を素直に更新すると、一見「パッチバージョンを上げるだけ」に見える
`arrow = "2.2.3"` への変更が、実は静かにビルドを壊す。

- Arrow 2.2.3 は Kotlin 2.4.0 でコンパイルされている。
- KSP (`arrow-optics-ksp-plugin` が使う `@optics` のコード生成基盤) の最新リリース (2.3.11) は
  Kotlin 2.3.20 までしか対応していない。
- したがって Arrow を 2.2.3 に上げると Kotlin も 2.4.0 に引きずられ、KSP が非対応の Kotlin
  バージョンで動くことになり、`@optics` のコード生成 (`OrderOptics.kt` 等が使う生成済み `Lens`/
  `Traversal`) が壊れる。

さらに Kotlin 2.3.21 は Spring Boot 4.1.0 が管理する `kotlin.version` と完全に一致するバージョンであり、
Kotlin を単独で動かすことにも制約がある (Spring Boot 側の BOM が前提とする Kotlin バージョンと
ズレると、`kotlin-spring` プラグインの挙動やコルーチン統合ライブラリのバイナリ互換性で
思わぬ問題を踏みうる)。

## 決定

以下の3つのバージョンを一体のものとして扱い、`gradle/libs.versions.toml` にその理由を明記する。

- `kotlin = "2.3.21"` (Spring Boot 4.1.0 の管理下と一致させる)
- `arrow = "2.2.2"` (2.2.3 は Kotlin 2.4.0 前提でビルドされており KSP と噛み合わないため禁止)
- `ksp = "2.3.11"` (Kotlin 2.3.20 までしか対応しないため、Kotlin を 2.3.21 より上げる際は
  まず KSP の対応状況を確認する)

このテンプレートを fork/clone してバージョンを上げる場合、**3つとも同時に見直す**こと。
どれか1つだけを上げると、ビルドが通ってから (`@optics` のコード生成が実行時ではなくコンパイル時に
壊れるため) 気づきやすいものの、原因の特定に時間がかかる。

## 帰結

**良い点**

- バージョンカタログのコメントに理由を書いておくことで、「なぜ最新パッチに上げないのか」を
  未来のメンテナが再調査せずに済む。
- 3つの依存関係の連動を一箇所 (`libs.versions.toml`) にまとめてあるため、アップグレード作業の
  最初の一歩が「このファイルを開く」で済む。

**トレードオフ・注意点**

- Arrow や KSP の新機能・バグ修正パッチを追従できない期間が生じる。特に KSP は Kotlin の
  マイナーバージョンごとに追従が遅れがちなライブラリなので、Kotlin を上げたいだけなのに
  KSP 側の対応を待たされる、という制約が今後も繰り返し起こりうる。
- `@optics` の生成コードに依存する箇所 (`OrderOptics.kt`) がある限り、KSP は外せない依存であり、
  この制約からテンプレートが完全に自由になることはない。Lens/Traversal の実利用箇所を減らせば
  KSP への依存自体を無くせるが、その場合はこのテンプレートが実演したい「Arrow の光学
  (optics) パターン」のデモを失うトレードオフになる。
